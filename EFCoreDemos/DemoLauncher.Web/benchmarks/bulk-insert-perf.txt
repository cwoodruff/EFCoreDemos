// * Takeaway *
//
//   Per-row SaveChanges is ~16x slower than AddRange at just 1,000
//   rows: one round trip and one transaction per row. Never save
//   inside the loop.
//
//   AddRange + one SaveChanges is the real fix, and EF's default
//   batching (42 rows per MERGE) already does the work.
//
//   "Tune MaxBatchSize up" backfires: 400-row MERGE statements were
//   1.2-2.4x SLOWER than 42-row ones, despite ~10x fewer round trips.
//   On localhost a round trip is cheap; the big MERGE is not. Leave
//   the default unless you've measured on your own network.
//
//   AutoDetectChanges off: noise. EF Core's Add doesn't rescan the
//   change tracker the way EF6 did - that tip is a decade old.
//
//   SqlBulkCopy is ~10-13x faster than AddRange at 10k-100k rows and
//   allocates ~11x less. No change tracking, no Ids read back. It is
//   the tool for imports and ETL, not for everyday saves.
